# Панель проектов через CLI

## Цель и объём

Пользователь выбрал встроенную установку панели в CLI iterm2-utils и поручил
опубликовать ветку и PR. Кнопка открывает новую активную вкладку с обычной zsh
в заданной папке и в том же окне. Повторный клик создаёт ещё одну вкладку;
команды в текущую сессию не вводятся. Нативный вариант уже проверялся отдельно
на iTerm2 3.7.6; новый CLI требует собственной проверки на фикстурах.

Варианты: инструкция с макетом (минимум кода, ручная установка) либо интеграция
в CLI (повторяемая установка/обновление/отмена с receipts). Пользователь выбрал
CLI. Только создание проектных профилей с последующим ручным редактированием
исходной панели не выполняет выбранный автоматизированный сценарий. Решение
исполнителя: существующий transaction engine плюс узкий адаптер официального SDK.
Нового фонового процесса, команд выбора проекта, собственного UI и APS нет.

## Внешний контракт

Feature: `project-launcher`. Флаг plan/install: `--project-launcher-config FILE`.
Первичная установка требует явный файл; повтор/update используют установленную
собственную копию. Флаг без выбранной feature отвергается до discovery.

```sh
python3 -m iterm2_utils plan --agent codex --features project-launcher --project-launcher-config /path/to/projects.json --json
python3 -m iterm2_utils install --agent codex --features project-launcher --project-launcher-config /path/to/projects.json --json
python3 -m iterm2_utils update --json
python3 -m iterm2_utils uninstall --features project-launcher --json
```

`--dry-run` выполняет чтение и планирование, без записей. `--agent` сохраняет
общую модель выбора пакета, но кнопки открывают shell, а не агента. Общие ресурсы
принадлежат явным feature×agent consumers; удаление одного consumer не убирает
панель другого. Существующие остальные функции не меняют поведения.

```json
{
  "profiles": ["Default"],
  "projects": [
    {"id": "project-a", "name": "Проект A", "path": "/path/to/project-a"},
    {"id": "project-b", "name": "Проект B", "path": "/path/to/project-b"}
  ]
}
```

`profiles` — непустой список уникальных имён существующих профилей, на которые
ставится панель. Владелец выбирает также профиль Codex/Claude, если он нужен.
Дубли имён в самом iTerm2, отсутствующие профили и конфликты разрешаются до записи.
`--parent-profile` — существующий профиль обычной оболочки для наследования новых
проектных профилей. Проектные профили явно открывают login shell; custom command
родителя не должен автоматически запускать агента. Профиль по умолчанию не меняется.

`projects` — непустой упорядоченный список. `id` — стабильный уникальный идентификатор
проекта; GUID детерминирован от namespace пакета и id, не имени или папки. `name`
непустое уникальное имя кнопки/профиля без управляющих символов. `path` — абсолютная
существующая папка; строки не являются shell-командами. Не создавать папки и не
клонировать проекты. Некорректный JSON, неизвестные поля, повторы и неподходящие типы
отвергаются понятным bounded finding без публикации private config contents.

## Нативная установка

Отдельный owned Dynamic Profiles файл содержит проектные профили, каждый со всей
панелью, наследованием по проверенному GUID и явным Initial Directory. В выбранных
исходных профилях меняются только `Show Status Bar` и `Status Bar Layout`; глобальное
положение — Bottom. Остальные профили, keymaps, цвета, иконки, hooks и shell startup
не меняются. Совместимость native формата ограничена проверенной версией iTerm2 3.7.6;
неизвестная версия не выдаётся за проверенную.

Компонент: `iTermStatusBarActionComponent`; knobs.action содержит `action:27`,
`version:2`, `applyMode:0`, `escaping:1`, title и parameter=GUID. Формат соответствует
образцу, полученному через штатный GUI. `knobs.action` — объект, не JSON-строка.
Обезличенный контракт одного компонента:

```json
{
  "class": "iTermStatusBarActionComponent",
  "configuration": {
    "knobs": {
      "base: compression resistance": 1,
      "maxwidth": 1.7976931348623157e+308,
      "base: priority": 5,
      "minwidth": "0",
      "shared font": "",
      "action": {"applyMode": 0, "escaping": 1, "title": "Проект A", "parameter": "project-guid", "action": 27, "version": 2}
    },
    "layout advanced configuration dictionary value": {
      "remove empty components": false, "auto-rainbow style": 0,
      "draw separator between status bar and terminal": false, "algorithm": 0
    }
  }
}
```

Верхний layout содержит `components` и существующий `advanced configuration`;
параметры последнего наследуются из живого снимка. Сохранять существующие foreign components,
порядок/advanced layout settings; добавлять свои кнопки в порядке config без дублей.
Позднее изменение owned resource выявляет CAS, а не разрешает перезапись.

Реальные materialized typed before обоих полей читаются из живого API. Отсутствующие
поля/неизвестные типы блокируют запись: JSON null, unset и подмена всего профиля
запрещены. Поля панели можно учитывать как один групповой адресный ресурс, чтобы
конфликт layout не приводил к отключению пользовательской панели отдельно.
SDK вызывается только при явном выборе этой feature/её receipt, в bounded дочернем
процессе выбранного существующего Python 3.11+ с iterm2. Не устанавливать SDK и не
запускать приложение автоматически. Pure builders получают подготовленный снимок
и возвращают ChangeSet, не подключаются к API и не пишут.

До изменения parent проверять связанные live sessions и семантику propagation.
Иной session override или неизвестное происхождение — конфликт без перезаписи.
Текущие сессии/процессы не закрывать, не перезапускать, не менять полный session
profile. Native readback после записи обязателен; timeout после отправки — неопределённый
результат с сохранением journal intent, а не автоматический повтор записи.

## Обновление, отмена и зависимости

Использовать существующие receipts, durable intent, CAS и восстановление после
прерывания; не создавать параллельную систему установки. before сохраняется от первой
записи, installed обновляется после подтверждения. Повтор не создаёт новые GUID/кнопки.
Входной файл можно удалить после установки: update читает собственную конфигурацию.
Изменение имени/папки при прежнем id сохраняет GUID.

Свою конфигурацию и Dynamic Profiles файл не заменять, если ими нельзя доказанно
владеть. При update с удалением проектов или uninstall перед удалением GUID проверить
все сохраняемые persistent profiles и live sessions (также новые), включая скрытые
кнопки и прямую привязку сессии к профилю. Собственные взаимные ссылки удаляемых
профилей не блокируют удаление. При атомарной замене собственного файла можно
также исключить старые поля панели сохраняемых owned-профилей, только если их
живые значения точно совпадают с принадлежащими пакету значениями и замена
устраняет ссылки. Все остальные поля и все сессии проверяются без исключений;
внешние/неизвестные ссылки блокируют. Сохранять
ресурс и receipt с conflict, не вычищать пользовательские кнопки и не закрывать сессии.

Для отмены: восстанавливать исходную панель только при точном типизированном совпадении
installed; более поздние изменения сохранять. Возврат parent может автоматически
повлиять на сессии: проверить их до операции. При атомарной замене собственного Dynamic Profiles файла сохраняемые проектные
профили могут ещё содержать прежние owned кнопки. Свежий worker inventory может
исключить только два поля панели, точно совпадающие с подтверждённым старым файлом,
если новая whole-file CAS версия устраняет все ссылки на удаляемые GUID. Другие
сырые поля и все live sessions проверяются полностью; изменённая или отсутствующая
панель/скрытая ссылка блокирует удаление.

До удаления целевых профилей должны
быть устранены только собственные подтверждённые ссылки. Нет полного inventory/API —
сохранить связанные ресурсы. Гонки между наблюдением и native write нельзя объявлять
устранёнными; проверять максимально близко к записи и ограничивать утверждения.

## Проверки и публикация

Все разработки/тесты только на TemporaryDirectory и fake Runner/SDK. Не применять
новый установщик к реальным настройкам разработчика и не читать auth или .env.
Проверить конфиг, dry-run, install/repeat/update без исходника, shared consumers,
точечные изменения, порядок, zsh, CAS/types/null rejection, interrupted intent,
propagation conflicts, external references и unavailable SDK. Запустить обязательные
unittest/check_skill и export/source проверки, собрать разрешённый архив.

Названия реальных вкладок и проектов, их состав, папки и пользовательский конфиг
конфиденциальны и не публикуются. Все примеры, тесты, спека и HTML используют
только вымышленные «Проект A» / «Проект B» и условные пути.

Публичные README, skill references, changelog и обезличенный HTML-пример описывают
команды, настройку API, выбор profiles и ограничения. Личные пути/GUID, приватные
журналы, скриншоты рабочего терминала и локальные планы в PR не входят. Матрица чётко
отделяет прошлую ручную native приёмку от нового CLI: его live install/uninstall
на реальном пользовательском состоянии не проверены фикстурами.

При недоступной после установки папке штатный iTerm2 предупреждает и открывает home;
новой защиты/фоновой проверки нет. Узкое окно может скрывать компоненты; Profiles
остаётся запасным входом. Браузер и localhost для установленной панели не нужны.
