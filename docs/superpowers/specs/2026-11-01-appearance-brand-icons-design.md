# Фирменные значки Mail/Облака и веб-репозитории

Статус: вариант B, спецификация и два новых цвета утверждены пользователем
01.11.2026.
База: `origin/main`, `e90b332` (влитый PR #5).

## Результат

В существующем `appearance` заменить условные письмо/облако фирменными
значками сервисов и добавить два готовых сочетания с Chrome для веб-проектов.
Визуальный вариант B: платформа крупнее, квадратный значок сервиса расположен
справа снизу. Почта — белая `@` на синем; Облако — фирменный белый контур на
синем; Chrome — официальный цветной знак. Это выбранные в макете версии.

Переиспользовать одну прозрачную составную PNG на сессию iTerm2. Внутри неё
могут быть непрозрачные фоны фирменных значков. Цель — различимость платформы
и сервиса при обычном размере значка вкладки, а не только в увеличенном макете.

## Рассмотренные варианты

- **A, рядом:** платформа и сервис занимают примерно равные части квадрата;
  каждый знак в размере вкладки меньше.
- **B, бейдж, выбран пользователем:** платформа остаётся крупнее, сервис
  перекрывает её справа снизу. Близко к текущему расположению, знаки крупнее.

## Ассеты и совместимость

- Обновить готовые пары `ios-mail`, `ios-cloud`, `android-mail`,
  `android-cloud`, сохранив их имена в существующих правилах.
- Добавить `chrome-mail` и `chrome-cloud`: всего девять встроенных имён.
  Отдельный встроенный `chrome` пока не нужен.
- Базовые `ios`, `android` и `kotlett` сохраняются. Для мобильных пар
  используются прежние символы телефона/Android из пакета.
- Поставлять согласованные SVG-исходники и готовые прозрачные PNG 128×128.
  Сохранить установку из checkout/release и работу после удаления исходников.
- Это явно заменяет решение предыдущей
  [спецификации](2026-11-01-repo-appearance-design.md#иконки-и-штатный-api)
  использовать только условные небрендовые знаки Mail/Cloud: пользователь
  запросил узнаваемые фирменные значки.
- Фирменные изображения получать из публичных источников; фиксировать
  происхождение и принадлежность брендов в существующих notices. Не объявлять
  чужую графику оригинальной работой пакета или автоматически покрытой MIT.
  Содержимое внутренних репозиториев в публичный пакет не переносить.

Готовые ассеты расширяют существующий набор; новый генератор, зависимости
установщика, схема JSON, настройка layout и загрузка картинок во время startup
не нужны. Runtime выбора каталога, chpwd/APS/ownership и сброс при выходе
за корни сохраняют проверенное поведение PR #5.

## Локальные правила

Сохранить пять существующих корней и цветов. Заменённые мобильные значки
обновляются через прежние встроенные имена. Добавить два локальных правила:

| Назначение | Значок | Утверждённый цвет из макета |
| --- | --- | --- |
| Веб Облака | `chrome-cloud` | `#D16D8A`, розовый |
| Веб Почты | `chrome-mail` | `#8B8FDC`, индиго |

Пути двух существующих репозиториев подтверждены локально; абсолютные корни
и итоговый персональный JSON остаются вне Git и публичного архива.
Результат — семь правил. Переход в подкаталог выбирает то же правило;
выход из всех семи корней возвращает стандартный цвет и скрывает иконку.

## Проверка и поставка

Проверить новые встроенные имена, валидность готовых PNG/SVG, доставку без
исходного checkout, сохранность текущих правил при install/update и экспорт
с корректными notices. Пройти обязательные проверки проекта и review.
После этого выполнить выборочный plan/dry-run/install `appearance` с обновлённым
локальным JSON. Остальные выбранные функции и чужие изменения сохраняются.

В собственных временных вкладках проверить шесть новых/обновлённых сочетаний,
неизменный Kotlett, цвета семи правил, подкаталоги и outside reset; оценить
читаемость в реальной панели. Рабочие вкладки пользователя не перезапускать.
Полные пути, сырой JSON и снимки с личными данными не публиковать. Итоговую
реализацию оформить отдельным PR в iterm2-utils, без автоматического merge.
