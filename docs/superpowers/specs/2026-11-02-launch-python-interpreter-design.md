# Один Python для проверки и запуска iterm2-launch

Статус: проект на согласование. Выбран подход: уточнение скилла и примеров без изменения CLI.

## Цель и причина

Следующий агент должен проверять SDK и запускать launcher одним интерпретатором.
Живая проверка SDK в одном окружении не подтверждает работоспособность команды
`python3` в другом. Сейчас требование «same interpreter» есть в скилле, но
примеры повторно используют имя из PATH. Кроме того, версия SDK осталась `pending`,
хотя README и матрица совместимости фиксируют живую проверку 2.23.

## Подходы

1. Уточнить инструкцию и примеры: выбрать Python, сохранить его абсолютный путь,
   проверить SDK и использовать этот путь дальше. Выбрано пользователем:
   закрывает обнаруженный пробел без изменения программного интерфейса.
2. Дополнительно выводить Python и SDK в диагностике CLI. Отложено: потребовало бы
   изменения кода и контрактов, а CLI уже использует `sys.executable` для SDK-процесса.

## Контракт инструкции

- В выбранном checkout или распакованном релизе определить `sys.executable`
  доступного `python3` либо явно указанного пользователем Python. Сохранить
  абсолютный путь как значение для этой попытки запуска, а не имя или shim из PATH.
- Сохранять путь, возвращённый `sys.executable`, без разыменования symlink до
  базового Python: это может изменить окружение virtualenv.
- Этим абсолютным путём проверить Python 3.11+ и фактический `import iterm2`, затем
  выполнить `launch-codex --help` и единственный вызов handoff либо resume.
  Проверки ограничены существующим бюджетом до 10 секунд на операцию.
- В примерах использовать одну именованную переменную `launch_python` с кавычками.
  При отдельных tool-вызовах передавать сохранённый абсолютный путь заново:
  shell-переменная не считается автоматически доступной в следующем вызове.
- Если меняются cwd или PATH, повторно проверять выбранный абсолютный Python
  в контексте вызова, не заменять его молча другим интерпретатором.
- Если SDK отсутствует, сообщить выбранный путь и недостающую зависимость до
  создания вкладки. Сохранить запрет автоматической установки, поиска чужих
  окружений и обхода отказа доступа. Явная установка по просьбе пользователя —
  отдельное действие, после которого prerequisite проверяется заново.
- Указать живую проверенную версию SDK 2.23. Это историческое доказательство из
  существующей матрицы, а не заявление о новой живой проверке на другом Python.

## Объём и границы

Меняются `skills/iterm2-launch/SKILL.md` и относящиеся к launch примеры README.
References меняются только при обнаружении противоречащих вызовов Python.
CLI, JSON, зависимости пакета, установщик и настройки терминала не меняются.
Публичная инструкция не привязывается к mise, версии Python 3.13 или личным путям.
Прежняя спецификация `2026-11-01-launch-api-resume-design.md` сохраняется как
историческая: её требование выбранного Python конкретизируется, запреты сохраняются.
После проверки исходника установленный скилл обновляется штатным bootstrap/CAS.

## Проверки и критерии приёмки

До изменения скилла зафиксировать поведение старой инструкции на вымышленных
сценариях: различающиеся Python, смена PATH/cwd, отсутствие SDK, путь с пробелами
и virtualenv с symlink. Затем проверить новую инструкцию на тех же условиях
свежими агентами; не считать структурный validator доказательством поведения.
Конкретный способ и объём поведенческих прогонов определяются планом.

Проверить исполнимость примеров выбора Python и импорта без создания вкладки,
структуру скиллов, согласованность README, требуемые репозиторием проверки и
bootstrap с точным совпадением установленного содержимого и receipt.
Успех: один сохранённый интерпретатор во всех вызовах, ошибки до создания вкладки,
нет личных путей и новых требований к менеджеру окружений.
Новая живая проверка handoff/resume не входит в эту правку документации.
