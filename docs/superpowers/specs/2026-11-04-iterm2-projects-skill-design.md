# Публичный навык iterm2-projects

## Назначение и границы

Отдельный переносимый навык для Codex и Claude Code позволяет управлять кнопками
папок в нижней панели iTerm2 обычными просьбами: добавить проект, убрать кнопку,
переименовать кнопку, изменить путь и показать текущий список. Он использует
существующую функцию `project-launcher` в iterm2-utils. Удаление проекта из панели
не удаляет его каталог и не закрывает вкладки или процессы.

Навык публикуется в открытом репозитории. Он не знает проектов разработчика,
не содержит их названий, состава, путей, GUID, снимков или конфигов. Все публичные
примеры и тестовые данные вымышленные: «Проект A», «Проект B», условные пути.
Данные конечного пользователя читаются и обрабатываются локально для его запроса.

Перенос, импорт и принятие во владение панелей, созданных вручную или другими
инструментами, в первую версию не входят. Не добавлять соответствующие команды,
миграции или обход проверок владения. Также не входят оформление вкладок,
статусы агентов, запуск агента, создание/клонирование/удаление каталогов.

## Подход

Рассмотрены расширение общего `iterm2-setup` и отдельный `iterm2-projects`.
Выбран отдельный навык: его удобно находить и вызывать для управления проектами,
не загружая инструкции по всем настройкам терминала. В `iterm2-setup` остаётся
короткое указание на него для операций с проектами.

Решение автора спеки: использовать штатные `plan`, `install`, `uninstall`,
`doctor` и их текущий JSON-контракт. Не создавать новые CRUD-команды или отдельный
механизм записи настроек. Кодовые изменения ограничены подключением третьего
skill bundle к существующему bootstrap, проверкам, тестам и публичному экспорту.

## Пользовательский сценарий

1. Определить запрошенную операцию и проект из просьбы и доступного контекста.
   Для «эту папку» использовать однозначно указанную рабочую папку; если контекст
   неоднозначен, уточнить. Отсутствующие имя кнопки или профиль назначения спросить
   одним коротким вопросом. Уже указанные значения и разрешения не спрашивать снова.
2. Выбрать имеющийся Python 3.11+, проверить доступность команды в актуальном
   checkout или распакованном release. Для применения панели нужны iTerm2 3.7.6,
   zsh, модуль `iterm2` в выбранном Python и разрешённый Python API. Путь выбранного
   runtime передавать штатным `ITERM2_UTILS_PYTHON`, когда требуется. Отсутствующие
   зависимости или разрешения не устанавливать и не выдавать автоматически.
3. Прочитать минимальное локальное состояние установки: launcher selection,
   parent profile и управляемый конфиг. Пути получать по правилам `resolve_paths()`
   с поддержкой HOME/XDG/CODEX_HOME, не считать фиксированный домашний путь истинным.
   Не печатать весь receipt, настройки агентов или окружение. Пользовательский
   явный запрос показать список разрешает краткий вывод его проектов в ответе,
   но не публикацию в Git, внешнем отчёте или тестовой фикстуре.
4. Подготовить отдельный приватный файл-кандидат вне публичного checkout с режимом
   `0600`. Для существующей установки основа — свежая собственная установленная
   копия конфига; исходный пользовательский JSON может отсутствовать. Receipt,
   установленный конфиг и Dynamic Profiles напрямую не редактировать. Исходный
   пользовательский файл тоже не перезаписывать без отдельного запроса.
5. Применить только запрошенное изменение, сохраняя все остальные поля, проекты,
   порядок, id, профили назначения и записанный parent profile. Запустить штатный
   `plan`, затем соответствующий `install --dry-run`, проверить блокирующие
   findings и выполнить такой же `install` с тем же файлом-кандидатом и выбором.
   Для изменения конфига использовать `install --project-launcher-config`, поскольку
   `update` не принимает новый конфиг. После операции выполнить `doctor --json`.
6. Перед применением убедиться, что локальная основа не изменилась с момента
   подготовки кандидата: сравнить сохранённые байты/отпечатки receipt и установленного
   конфига с текущими. При отличии заново прочитать состояние и построить изменение;
   не применять устаревшую копию. Существующие CAS и проверки CLI не обходить.
7. Сообщить фактический результат: что добавлено/удалено/переименовано либо почему
   операция заблокирована. Успешный API readback не объявлять проверкой отображения
   и клика. Собственный временный кандидат удалить по завершении; при неопределённом
   исходе первой установки сохранить его локально с `0600` и сообщить путь для
   восстановления. Пользовательские исходники не удалять.

## Операции

| Запрос | Поведение |
| --- | --- |
| Добавить проект впервые | Собрать минимальный полный конфиг; явно определить agent consumer, существующий профиль назначения и parent profile; использовать только `project-launcher`. |
| Добавить в существующую панель | Добавить запись в конец; создать один новый устойчивый id, сохранить его в кандидате для всех повторов. |
| Повторить уже выполненное добавление | Если запись уже соответствует просьбе, сообщить, что она есть; не добавлять дубль и не выполнять запись. |
| Переименовать / изменить путь | Изменить только требуемые поля найденной записи; сохранить id/GUID и положение в списке. |
| Убрать одну из нескольких кнопок | Исключить только найденную запись; применить оставшийся непустой конфиг через plan/install. |
| Убрать последнюю кнопку | Не отправлять пустой список; выполнить `uninstall --features project-launcher --dry-run --json`, затем соответствующий uninstall. Другие функции пакета сохраняются. |
| Показать список | Только локальное чтение; не запускать install/update/recovery. |

Проект разрешается по id, имени или явному пути. Неоднозначное совпадение требует
уточнения, а не удаления всех совпадений. Отсутствующая запись при удалении —
no-op с сообщением. Если тот же путь уже есть под другим именем, уточнить, нужен ли
второй ярлык. При совпадении имён разных проектов не выбирать автоматически.

Директория добавляемого проекта и новый путь должны существовать. Удаление проекта
с исчезнувшей папкой допустимо: доступность проверяется для нового конфига. Новый id
генерируется один раз независимо от имени и пути (например, UUID); существующие id
не пересчитываются. JSON формируется структурно, пути не склеиваются в shell-код.

Панель и конфиг общие для записанных `project-launcher` consumers. При обновлении
использовать именно их набор из receipt: не добавлять второго агента и не снимать
существующее владение. Удаление последнего проекта отключает общую функцию у всех
её текущих consumers; это кратко объясняется как следствие удаления всей панели.
При запросе отключить функцию только для одного агента использовать штатный
agent-scoped uninstall и объяснить, что общая панель другого consumer останется.

## Владение, конфликты и границы восстановления

Отсутствие receipt допускает штатную первую установку, но не означает права
изменять существующие ручные кнопки/профили или присваивать их идентификаторы.
Если пользователь просит изменить неуправляемую панель, сообщить об отсутствии
поддержки её импорта; не реконструировать её по снимку и не выполнять удаление
напрямую через SDK, plist, defaults или AppleScript. `--adopt-legacy` не является
импортом project-launcher и не применяется для этой задачи.

Чужие правки, занятые профили, неоднозначные имена, неизвестная версия, отсутствующий
SDK и неполный inventory обрабатываются штатным CLI. При конфликте остановить
применение, сохранить данные и объяснить пользователю конкретный следующий шаг.
Не закрывать его сессии, не сбрасывать поля в null, не править receipt и не
подменять владение. При необходимости пользователь сам завершает связанные вкладки.

Не повторять native запись вслепую после timeout. Если предыдущая операция оставила
journal, read-only диагностика его не восстанавливает; дальнейшую штатную изменяющую
команду выполнять осознанно как recovery, без прямого редактирования journal.
Существующие ограничения неатомарной проверки состояния и версии iTerm2 сохраняются;
навык не заявляет их устранение. Если plan блокируется артефактами незавершённой
установки, не удалять эти файлы: объяснить предусмотренное CLI восстановление.

## Поставка и затронутые места

- `skills/iterm2-projects/SKILL.md`: короткий самостоятельный entry с триггерами
  естественного языка и одной ссылкой на bundled reference.
- `skills/iterm2-projects/references/projects.md`: схема, точные команды и особенности
  чтения локальной базы/создания кандидата, удаления последней кнопки и конфликтов.
  После bootstrap все относительные ссылки остаются внутри bundle; частные навыки
  и соседний checkout не являются зависимостями.
- `iterm2_utils/skill_install.py`, `iterm2_utils/cli.py`: bundle `iterm2-projects`
  и значение `bootstrap-skill --skill iterm2-projects --agent codex|claude|both`.
  Использовать существующие независимые bootstrap receipts и CAS. Default
  `iterm2-setup` и ограничение `iterm2-launch` только для Codex сохраняются.
- `tools/check_skill.py`, `tools/check_export.py`, bootstrap/export tests:
  третья поставка и её файлы охвачены проверками и архивом.
- README, CHANGELOG, setup skill/reference и инструкция панели: точка входа,
  установка и границы возможностей без дублирования большого workflow.

Bootstrap копирует только навык и не устанавливает панель. Документация показывает
сначала dry-run bootstrap, затем явную установку выбранному хосту. Навык можно
прочитать прямо из репозитория; появление в discovery текущего сеанса не обещается.

## Приёмка

Автоматические тесты используют TemporaryDirectory HOME/Paths и fake Runner/SDK.
Нельзя читать или менять реальные настройки, auth, .env или запускать GUI во время
разработки. Проверить bootstrap для Codex, Claude и both, отсутствие записей dry-run,
повтор/обновление, независимость существующих навыков, сохранение чужих изменений,
полноту и самодостаточность bundle в release, прежний default.

Для поведения агента до написания навыка подготовить отдельные вымышленные контрольные
задачи и снять baseline: добавление без исходного JSON, удаление одной/последней
кнопки, переименование со стабильным id, shared consumers, неоднозначный запрос,
конфликт/неуправляемая панель, исчезнувшая папка и устаревшая основа кандидата.
Повторить задачи с навыком в свежих процессах по правилам writing-skills; контрольные
значения не переносить в примеры навыка. Отдельно проверять обнаружение нового имени.
Недоступную авторизацию тестового агента отметить ограничением; структурный validator
не выдавать за поведенческую проверку. Нельзя использовать рабочие личные конфиги
или читать секреты ради запуска проверки.

Обязательные проверки: unittest discover, check_skill, check_sources, check_export,
build_release и просмотр diff на приватные данные. Реальную приёмку iTerm2 и поведение
модели указывать отдельно от fixture/структурных проверок. Планы и сырые агентские
логи остаются локальными и игнорируемыми. Новая функция считается спроектированной
после проверки этой спеки; реализация начинается после её согласования и плана.
