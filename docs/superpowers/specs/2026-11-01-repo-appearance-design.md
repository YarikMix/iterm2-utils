# Оформление вкладок по репозиторию

Статус: согласована пользователем 01.11.2026; реализация после согласования плана.
База: `origin/main`, `24789a8e861cc676982cc4990ba7bce7a3b6cf46`.

## Задача и выбранное поведение

Добавить в публичный iterm2-utils переиспользуемую opt-in функцию `appearance`.
Она назначает цвет и иконку вкладке по папке запуска. iTerm2 сам отображает
оформление через свои штатные возможности; пакет выбирает параметры и
управляет их установкой. Отдельного плагина iTerm2 или агента не требуется.

Первая версия обслуживает интерактивную zsh-сессию и запуск Codex, как в
исходном запросе. Интеграция с Claude не заявляется. Оформление назначается:

- при первом запуске интерактивной оболочки iTerm2 в подходящей папке;
- при интерактивном запуске `codex` из подходящей папки, включая `resume`/`fork`.

Последующие обычные `cd` не меняют оформление. Выбор задач/эпиков в разговоре
не отслеживается. Оформление сохраняется после завершения Codex; новый
интерактивный запуск из другой зарегистрированной папки назначает её оформление.
При отсутствии совпадения существующее оформление не меняется.
`codex --help`, `exec`, `review`, `login`, другие служебные команды и неинтерактивные
оболочки не запускают механизм. Папка — физический `$PWD` вызывающей оболочки;
не анализировать команды модели и не извлекать рабочую папку из истории диалога.

## Подходы

1. **Штатные профили и Automatic Profile Switching.** Мало своего runtime,
   но переключение реагирует на последующие изменения папки и меняет целый
   профиль. Это не выбранная пользователем семантика назначения при запуске.
2. **Отдельный плагин/постоянный наблюдатель.** Позволил бы отслеживать любые
   изменения, но для назначения при запуске добавляет отдельный жизненный цикл
   и дублирует существующие установщик и оболочку iterm2-utils.
3. **Новая функция пакета — рекомендуемый подход.** Переиспользовать selection,
   ChangeSet, transaction engine, receipts/CAS, runtime releases и общий dispatcher.
   Короткоживущий helper вызывает официальный Python API для явной сессии.
   Нет второго установщика, постоянного демона, MCP или agent hooks.

Место функции в пакете следует из новой просьбы пользователя. Конкретное имя
`appearance`, JSON-формат и перечисленные ниже границы — предложение исполнителя.

## Персональная конфигурация

Устанавливающий пользователь передаёт JSON-файл правил в `plan`/`install`,
например через `--appearance-config /absolute/path/rules.json`, только вместе
с явно выбранной функцией `appearance`. Не вводить отдельное семейство команд
регистрации проектов. Bootstrap функции не включает.

Каждое правило содержит только:

- `root`: абсолютный корень репозитория;
- `color`: цвет вкладки в виде `#RRGGBB`;
- `icon`: встроенное имя иконки или абсолютный путь к пользовательскому PNG.

Корень и его подкаталоги совпадают с правилом, похожие соседние имена — нет.
Для вложенных зарегистрированных корней выигрывает наиболее длинный;
повтор одного физического корня отклоняется как неоднозначный.
Пути нормализуются с учётом симлинков; недоступный внешний диск не сканируется,
не создаётся и не подменяется внутренней копией. При недоступности цели правило
не применяется; пакет остаётся работоспособным без подключённого диска.

Перед записью проверяются структура JSON, абсолютные пути, цвет, известное имя
иконки либо доступный PNG. Конфигурация не является кодом: без eval, команд,
интерполяции shell и загрузки иконок по URL. Встроенные и пользовательские иконки
копируются в установленный runtime/data, чтобы установка не зависела от checkout
или исходного PNG. Правила копируются в локальный конфиг пакета вне release;
после установки исходный JSON не требуется. Не включать локальные пути и правила
автора в Git, примеры, release archive или публичные отчёты диагностики.

Первоначальный локальный набор пользователя: зелёная Почта Android,
бирюзовое Облако Android, оранжевая Почта iOS, синее Облако iOS и фиолетовый
Kotlett. Абсолютные пути и точные цвета уже описаны в отдельном локальном
черновике; его персональное содержимое в публичную спецификацию не переносить.

## Иконки и штатный API

Предоставить три базовых символа платформ: `ios` (iPhone), `android`, `kotlett`,
и пять готовых вариантов: `ios-mail`, `ios-cloud`, `android-mail`,
`android-cloud`, `kotlett`. Для Mail и Cloud использовать различимые символы
почты и облака, без заявления об использовании официальных брендовых логотипов.

Вкладка iTerm2 имеет один custom icon. Поэтому две видимые сущности —
заранее подготовленная составная PNG с прозрачным фоном. Пользователь может
заменить её своим PNG. Иконки поставляются готовыми: установка не требует
графического редактора, генеративного API или библиотеки обработки изображений.
Права на ассеты и их происхождение фиксируются в существующей документации
лицензий; никаких скачиваний картинок при запуске оболочки.

Helper меняет только сессионные `Tab Color`/использование цвета и
`Icon Mode`/`Custom Icon Path`, используя официальный Python API iTerm2.
Изменения глобального Default и замена всего профиля не нужны.
Использовать валидный явный UUID собственной сессии; никогда не выбирать
активную вкладку. При двух противоречащих источниках ID действие отклоняется.

## Интеграция в существующий пакет

- Добавить `appearance` как явную Codex-only функцию первой версии и
  интегрировать её в существующие selection, plan/install, doctor,
  update/uninstall. Поддержку другой платформы/агента не достраивать заранее.
- Использовать штатный общий `runtime/codex.zsh`, а не оборачивать неизвестные
  пользовательские функции и не создавать второй competing dispatcher.
  Сохранить `--no-daemon`, классификацию команд, аргументы, код выхода,
  restore и выбранные возможности остальных агентов.
- Начальное назначение оболочкой выполняется однократно для её сессии;
  повторный source не дублирует hooks/действия. `chpwd`/постоянные timers не нужны.
- Учесть существующее APS-правило `&codex`: оно не должно сбрасывать цвет/иконку
  при старте Codex или restore. Допустим короткоживущий обработчик перехода
  запуска, завершение которого ограничено timeout; постоянный наблюдатель не
  допускается. Точный способ синхронизации — решение реализации с live-проверкой.
- Требования: macOS, zsh, поддерживаемый Python 3.11+ и библиотека `iterm2`
  именно в выбранном runtime Python, включённый/разрешённый Python API.
  Переиспользовать уже подходящий интерпретатор/модуль. Недостающую зависимость
  обнаруживать и сообщать до установки; не запускать скрытый pip на старте.
- Короткий timeout API, отсутствие ID/API/ассета или ошибка оформления не
  блокируют запуск Codex и не превращают его успешный выход в ошибку.
  Диагностика ограниченная, без содержимого команд, токенов и пользовательских
  конфигов. Не выводить успешное применение, если API его не подтвердил.
- Runtime payload/export allowlists должны включать готовые ассеты. Исходники
  helper, установленные assets и документация работают после удаления checkout.
- `plan`/dry-run не запускают GUI, Python API и оболочку пользователя и ничего
  не пишут. Builders описывают ChangeSet. Тесты используют TemporaryDirectory
  HOME/Paths и fake adapters, не читают реальные agent/iTerm settings автора.

## Обновление и удаление

Правила и ассеты учитываются существующими receipts/CAS. Update использует
установленные правила, не требует исходный JSON и сохраняет чужие изменения.
Повторный install без нового JSON использует валидный установленный набор;
при первой установке без правил возвращает понятную ошибку до записи.
Переданный при install новый JSON означает явную замену собственного набора.
Коллизии с вручную изменёнными owned файлами требуют обычного разрешения
конфликта, а не молчаливой перезаписи.

Uninstall отключает только appearance и удаляет только его неизменённые
owned-ресурсы; общие shell/runtime остаются для других функций. Уже работающие
пользовательские вкладки не сбрасываются и не перезапускаются; текущее визуальное
оформление в них может сохраняться до закрытия. Новая сессия после удаления не
получает оформление. Не восстанавливать целые конфиги из backup поверх чужих
изменений и не редактировать мобильные репозитории.

## Проверки и приёмка

1. **Правила:** пять вариантов, корень/подкаталог, граница пути, симлинки,
   вложенные корни, дубликаты, отсутствующий SSD, неверный цвет/JSON/иконка,
   имена с пробелами и shell-метасимволами как данные.
2. **Runtime:** только своя сессия, неверный/противоречивый ID, нет API,
   отказ/timeout, нет совпадения, сохранение аргументов/кода выхода Codex,
   source дважды, обычный cd, служебные команды и restore.
3. **Lifecycle:** явный opt-in, dry-run без записей/GUI, повторный install,
   update без исходных файлов, сохранность чужих настроек, частичный uninstall,
   совместное использование shell/runtime и отсутствие зависимости от checkout.
4. **Поставка:** release и runtime содержат PNG и лицензии; README, skill,
   features/troubleshooting и compatibility описывают новую опцию и ограничения.
5. **Живая проверка после разрешённой локальной установки:** пять сочетаний в
   собственных временных вкладках, читаемость составных значков в реальном
   размере, запуск Codex с существующим APS-профилем и restore, отсутствие
   переключения на обычном cd. Не путать fixture tests с live acceptance.

Обязательные проверки репозитория: `python3 -m unittest discover -v`, zsh-тесты
затронутого лаунчера/restore, `python3 tools/check_skill.py`, проверки runtime
payload, export и сборки release. Live-проверки выполнять отдельно и сообщать
фактическую матрицу; не закрывать пользовательские вкладки и не обходить UI/TCC.

## Границы первой версии

Нет отдельного магазина плагинов, демона, GUI редактора правил, автоматического
определения эпика/задачи, поддержки произвольных shell или дополнительных агентов.
Пользователь может добавлять любое число репозиториев и свои PNG через JSON.
Разработка функции и персональное включение на машине — отдельные действия;
изменение репозитория не включает её на машине разработчика автоматически.
