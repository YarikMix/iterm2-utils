# Изоляция запуска Codex и принадлежность оформления терминалу

Статус: утверждена пользователем. Одна задача охватывает `launch-codex` и `appearance`.

## Цель

Служебные оболочки launcher и команды агента не должны менять цвет, иконку
или сохранённое оформление родительской вкладки. Обычная интерактивная оболочка
продолжает показывать проект своего текущего каталога.

## Подходы

- Флаг служебного запуска: launcher выставляет признак, оформление пропускает
  помеченные вызовы. Требует, чтобы каждый сторонний вызывающий его выставлял.
- **Выбрана изоляция и проверка принадлежности:** launcher не передаёт своей
  служебной оболочке идентификаторы родительского терминала; оформление независимо
  проверяет соответствие фактического терминала оболочки указанной сессии iTerm2.

Это небольшое исправление существующих механизмов. Используются zsh, стандартная
библиотека Python и официальный SDK iTerm2; новые зависимости не нужны.

## Изоляция launcher

Перед проверкой эффективного конфига `launch-codex` создаёт отдельное окружение
дочернего процесса без унаследованных `ITERM_SESSION_ID` и `TERM_SESSION_ID`.
Очистка касается только служебных процессов проверки, включая shell startup.
Окружение родителя не изменяется. Определение целевого окна и остальные проверки
запуска сохраняют нужный им контекст родителя.

Проверка по-прежнему выполняется в заданном cwd через пользовательскую login shell:
нельзя обходить её startup, подменять effective config или отключать защиту wrappers.
Сохраняются `CODEX_RESTORE_NO_AUTO=1`, deadlines, argv и статусы обоих режимов:
handoff и resume. До создания вкладки проверка не меняет сессионные свойства
родителя, в том числе appearance snapshot.

Настоящая новая вкладка получает собственную терминальную привязку от iTerm2.
Очистка служебного окружения не переносится в её стартовую команду и не отключает
её оформление, статусы, restore или штатную функцию `codex`.

## Проверка принадлежности оформления

Для любой изменяющей операции `appearance` недостаточно UUID из окружения.
Нужен фактический терминал вызывающей оболочки, совпадающий с терминалом
явно указанной сессии iTerm2. Наличие произвольного PTY само по себе недостаточно:
команда агента может работать в другом PTY с унаследованным UUID родителя.

Данные собственного терминала фиксируются до перенаправления потоков в helper.
Проверка не должна требовать TTY на stdin/stdout detached worker: его pipes
и существующий supervisor являются штатным транспортом. Способ получения
терминала оболочки и сопоставления устройств оставлен исполнителю; сравнение
должно учитывать алиасы пути к одному устройству и не угадывать терминал по фокусу.

До подтверждения соответствия разрешены только необходимые чтения. При отсутствии
терминала, несовпадении, неоднозначности или ошибке API оформление пропускается.
Нельзя назначать или сбрасывать цвет/иконку, создавать, инвалидировать, очищать
либо восстанавливать snapshot чужой сессии. Проверка охватывает `shell`, `launch`
и `return`, включая отложенные observer-записи и переходы APS. Цель остаётся
привязанной к проверенной сессии на всём протяжении операции.

Read-only probe сохраняется отдельной проверкой доступности API: её успех
не разрешает последующую запись без проверки принадлежности. Нет fallback
к активной вкладке, polling, постоянного процесса или завершения чужих процессов.
Это защита от ошибочно унаследованного контекста, а не изоляция от вредоносного
процесса с доступом к тому же пользовательскому API iTerm2.

## Сохраняемое поведение

- Старт обычной интерактивной zsh и пользовательский `cd` применяют правило
  текущего физического каталога; выход из всех правил отключает Tab Color
  во всех поддерживаемых вариантах темы и скрывает кастомную иконку.
- Вручную запущенная вложенная интерактивная оболочка в том же терминале
  продолжает оформлять свою вкладку. Оболочка без терминала и оболочка агента
  в другом PTY не меняют родительскую вкладку, даже при унаследованных UUID.
- Сохраняются запуск и возврат Codex, существующие APS/restore, отмена старого
  helper и ограниченный бюджет ожидания. Ошибка оформления не отменяет `cd`
  или запуск Codex и не меняет их код выхода.
- JSON-правила, цвета, ассеты, пользовательские PNG, профили, панель проектов
  и чужие shell hooks сохраняются. Новых настроек и публичных флагов не требуется.

Это уточняет требование [оформления по cwd](2026-11-01-appearance-cwd-design.md):
«собственная интерактивная сессия» определяется принадлежностью терминала,
а не одним флагом interactive. Сохраняется проверка через login shell из
[спецификации запуска](2026-11-01-launch-api-resume-design.md), но её служебное
окружение больше не получает привязку к родительской вкладке.

## Проверка и поставка

Разработка использует TemporaryDirectory HOME, fake Runner/SDK и реальные
изолированные PTY там, где проверяется принадлежность терминала. Не читать
пользовательские настройки и не обращаться к рабочим вкладкам из unit-тестов.

Обязательные сценарии:

1. Оба режима launcher: родительские UUID отсутствуют в служебном окружении,
   остальные настройки сохранены; родитель не изменён; новая вкладка имеет
   собственную привязку и штатный запуск.
2. Регрессия целиком: родитель в общей папке, проверка launcher в другом проекте,
   служебная interactive shell с pipes. Цвет, иконка и snapshot родителя неизменны.
3. Те же гарантии при чужом PTY с унаследованными UUID; отсутствие/конфликт ID,
   закрытая сессия, отсутствующий терминал и ошибки API не разрешают запись.
4. Собственный PTY: старт, обычный `cd`, подкаталог, переход между правилами,
   выход наружу, вложенная shell, быстрые переходы, launch/return под APS.
   Pipes supervisor не блокируют правильный вызов; при отказе нет даже
   промежуточных изменений snapshot.
5. Обязательные unittest, shell/skill и относящиеся export/release проверки;
   поставка обновлённых shell/runtime и CLI проверяется совместно.

После реализации и ревью — штатный plan/dry-run перед локальным обновлением
launcher и appearance с сохранением выбранных функций и чужих настроек.
Установщик не перезапускает существующие оболочки. Для загрузки нового shell hook
нужна новая оболочка; ограничения старых вкладок явно сообщаются пользователю.

Живая приёмка проводится отдельно от разработки: с предварительным предупреждением
создаются только собственные тестовые вкладки, проверяются оформление родителя,
отдельное оформление ребёнка и обычный `cd`. Рабочие пользовательские сессии,
профили и разрешения не изменяются ради проверки. Закрываются только собственные
тестовые вкладки с известным результатом; неопределённый запуск не повторяется.
Автоматические проверки не подменяют живую приёмку. Её результаты идут в отчёт,
а не в эту спецификацию.
